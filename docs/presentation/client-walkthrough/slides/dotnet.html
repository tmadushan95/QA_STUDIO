Architecture · .NET API

Clean Architecture with CQRS

API

Endpoints, security, gateway, error shape. Knows HTTP.

Infrastructure

EF Core, Dapper SQL, repositories, cache. Knows technology.

Application

One folder per use case: command or query, validator, handler.

Core (domain)

Entities and rules. Depends on nothing.

Dependencies point inward

Core never mentions EF Core, HTTP or JSON, so rules are tested without a database.

Commands and queries

Writes use a rich model and one transaction (EF Core); reads use fast hand-written SQL (Dapper).

One pipeline for every request

Dispatcher: Logging, then Validation, then Handler. Nothing to register by hand.

For architects in the room. Clean (Onion) Architecture: four projects, and the dependency rule says arrows only point inward. The domain in the middle knows nothing about databases or the web. Application declares interfaces such as IDashboardReader; Infrastructure implements them; dependency injection connects them at start-up. CQRS: every use case is either a command (changes state) or a query (only reads), each with exactly one handler, in its own folder: Application/Features/TestCases/CreateTestCase. A feature is easy to find, change or delete. This is the vertical-slice layout. We wrote a small mediator (the Dispatcher) with pipeline behaviours, so logging and validation are applied in one place for every request. Writes go through EF Core repositories and a unit of work; reads for lists and dashboards use Dapper with hand-written SQL, which is faster and clearer for aggregates.
