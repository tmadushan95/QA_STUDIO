Values come in as {{data.name}} from parameters, or {{var.name}} remembered by an earlier step.

Action registry

Each step type registers a schema, a run function and form hints. New steps plug in; the runner never changes.

One schema, three uses

The same Zod schema validates a step, documents it and draws its form in the editor. No drift.

An interpreter

Checks every step first, then runs them in order and records each result.

Custom steps

A project’s own step made from standard steps, treated like any built-in one.

This is the heart of the product and the reason the worker is in Node. A test step is a small JSON document: an action name and its parameters. The registry maps each action name to its definition: a Zod schema saying which parameters are valid, a function that performs it with Playwright, and UI metadata (label, group, fields). Because one schema drives validation, documentation and the editor form, they can never disagree. Adding a new standard step, for example “double-click”, makes it appear in the editor with no frontend change. Custom steps use the Composite pattern: one step made of other steps, with inputs. The worker is split into packages, each with one job: shared schemas, automation-core (the step engine), execution-engine (run manager and Playwright), test-case-import (Excel), agents and llm (AI), knowledge (search index) and reporting.
