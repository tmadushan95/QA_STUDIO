Architecture · A run, end to end

One run, followed end to end

1

Press Run

POST /api/runs with cases, users and mode.

2

Gateway

The API forwards it to the worker.

3

Run manager

Reloads cases, queues one job per case and user.

4

Browser

Playwright opens Chromium and signs in.

5

Validate first

Every step is checked; any problem blocks the case.

6

Run steps

In order, with screenshots and a trace.

7

Save

Results batched to the API and SQL Server.

8

Live update

Run History redraws as each case ends.

Now the second shape of request: running tests. The API does not implement runs itself, so the gateway forwards the request to the worker, transparently. The run manager keeps a queue, limits how many browsers run at once, supports cancel, and reloads the cases from the database before the run, so it never uses stale data. Step 5 is a key safety property: the step interpreter validates every step of a case before running any of them. An unknown action, a bad parameter or a missing value means the case is “blocked” and nothing runs. You never get a half-executed test that left data in a strange state because of a typo. Results are written behind in batches (fast) but a save is only confirmed once committed. If the worker restarts, runs that were in progress are closed as cancelled, so history never lies.
