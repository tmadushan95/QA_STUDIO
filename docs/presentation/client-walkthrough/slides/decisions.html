Engineering quality · Key decisions

Key decisions we made, and why

DecisionWhy
Generic, data-only steps, not per-app codeWorks on any web app; testers can edit; AI output can be checked
SQL Server behind a .NET API; Node stays the runnerEnterprise storage and security; keep the proven Playwright engine
TypeScript end to end in the workerOne language with the web app, no Python hybrid
Each project has its own address, sign-in and accountsMany client apps in one installation
EF Core for writes, Dapper for readsTransactions where needed, fast SQL for lists and dashboards
Move worker features to .NET in stagesNo big-bang rewrite and no web app change
Aspire for development onlyHot reload and tracing for developers; a simple install for testers
Every one of these is recorded as an Architecture Decision Record in docs/adr, with the context, the options considered and the trade-offs. Offer to share them with the client’s architects. The one to explain if there is time is the staged move to .NET (ADR 0010). We already moved the dashboard, run-history reads, the page list and parameter values. Each move follows the same recipe, and the gateway means the web app never changes. This shows the client the platform has a clear, low-risk path to evolve. Mapping to ADR numbers: generic steps 0004, SQL Server and .NET 0005, TypeScript only 0002, per-project connection 0006, Dapper reads 0008, staged move 0010, Aspire 0012.
