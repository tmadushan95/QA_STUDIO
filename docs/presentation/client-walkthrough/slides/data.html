Relational tables

Projects, versions, suites, test cases, accounts, audit. Deletes are restricted down the tree; every editable row has a row version, so a stale save gets a clear conflict.

JSON documents

Runnable scenarios, runs and settings, whose shape belongs to the step engine. Status and version are columns for fast filtering. Evidence files stay on disk.

The hierarchy from the business brief is Project, then Test suite, then Test case. Versions sit beside suites. A pragmatic choice worth explaining: test cases are proper relational tables, but scenarios and runs are stored as JSON documents in SQL Server, with a JSON validity check. Their shape belongs to the step engine and changes with it, and nobody needs to query inside them with SQL. Normalising them would mean keeping two schemas in step for no benefit. Safety in the schema: deletes are restricted, so one click cannot remove a whole project’s library; row versions give optimistic concurrency; passwords and AI keys are stored encrypted. Screenshots and traces are files on disk, listed in the run. Measured performance from our database notes: fetching one case takes about 7 to 30 ms, and a page of cases by suite about 6 to 14 ms. Free-text search is the slowest operation today, at a few seconds; mention this only if asked.
